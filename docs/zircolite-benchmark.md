## 三、口径与局限

1. **百分比 = 我们覆盖的 Zircolite 能力点 ÷ Zircolite 的能力点**，逐项人工核对得出。
   能力点的划分与计数是判断，不是测量——它衡量「对标覆盖度」，**不等于工程质量或实用价值**。
2. **只有「规则量」一行是实测**（数文件里的规则条数）；性能那一行的分母是 Zircolite 的机制清单，
   不是耗时比值。Zircolite 的 benchmark 跑在 EVTX 上、本机未复现，**不做耗时对比**。
3. **`57%` 是 9 个功能域的简单平均**，未加权——权重取决于用途（只看 Windows 应急则界面与规则量更重要，
   看 Linux 则格式解析那一行会掉到 20%）。
4. **这个百分比不衡量我们独有的能力**（AI 研判、证据溯源、覆盖度三态、威胁情报、人工确认、
   provenance 分层导出、多日志类型）。这些在 Zircolite 里没有对应项，因此**不进分母**——
   换句话说，57% 只说明「它有的我们补到哪儿了」，不说明「我们整体做到了几成」。
5. 最大的三处差距：**字段处理（20%）、检测性能（33%）、导出格式（38%）**。
   其中字段处理的差距最实在：Base64 / 沙箱变换缺失会直接让一批 Sigma 规则转不过来。

## 四、低于 80% 的 7 个功能域：能不能补、难度、改动、后果

### 先看「卡住的到底是什么」（实测，不是估计）

对 2418 条候选规则逐条统计跳过原因，**215 条跳过**的成因分布：

| 阻塞项 | 条数 | 难度 | 改动位置 | 能拿回 |
|---|---:|---|---|---:|
| `windash` 修饰符 | **82** | 低 | 转换器：值侧展开 5 种破折号变体（`-` `/` `–` `—` `―`）→ 现有的 `any_contains` 多值即可表达 | +82 |
| `logsource` 无权威 EventID | 60 | 中高 | 需**外部权威映射表**（Sigma taxonomy）；猜错 = 规则变死规则 | 有条件 |
| 取反 / 条件展开分支过多 | 26 | 中 | 转换器放宽 DNF 分支上限；代价是规则更慢 | +26 |
| `cidr` 修饰符 | 17 | 低 | 引擎加一个 `in_cidr` op——**`whitelist.py` 里 `ip_network` 逻辑已存在**，复用即可 | +17 |
| 中间通配取值（`a*b`） | 12 | 低 | 转换器：转成现有的 `regex` op（注意转义） | +12 |
| `base64offset` 修饰符 | 7 | 中低 | 转换器：值侧做 3 种偏移的 base64 编码 → `any_contains` | +7 |
| 字段名为空 | 6 | 低 | 转换器：`|re` 这类**只有修饰符的键**隐式指向 `keywords` | +6 |
| `fieldref` 修饰符 | 3 | 中 | 引擎加「字段比字段」谓词 | +3 |

**其中 107 条（windash 82 + base64offset 7 + 空字段名 6 + 中间通配 12）只需改转换器，不碰引擎。**

### 逐域结论

**① 字段处理 20% —— 建议做（性价比最高）**
- 要改：转换器加 `windash` / `base64offset` / `|re` 隐式字段名；解析器派生 `Hashes` 拆包字段（SHA256/MD5 分列）。
- 难度：低到中。实测可解锁 **95 条规则**（82+7+6）。
- 后果：规则量上去后**必须重跑误报筛查**（上一轮 11 条因命中正常流量被剔除，是真实先例）。
- **不建议做的部分**：沙箱 Python 变换。`AGENTS.md` 明确「只读日志、不执行」，引入可执行变换要自己造沙箱，安全面大、收益是「对齐 Zircolite」而非用户需求。

**② 检测性能 33% —— 建议做，但方向要对**
- **照搬 Zircolite 的编译展平内核不值得**：实测瓶颈在规则匹配（15.75s），解析只有 0.89s——它的 C 内核是为它的展平路径服务的，我们没有那个瓶颈。
- 正解是**字面量倒排索引**（项目文档里已记录）：69 条 `keywords`/`any_contains` 规则没有必要条件、只能全量扫描。
- 并行 worker 可行（中难度），但后果要认：内存 ×N（当前 5.0× 文件），且 `_POOL_STATE` 是 `threading.local`、要改成进程内。

**③ 日志格式解析 50% —— 建议做一半**
- 值得做（低难度）：**压缩包自动解压**（zip/gzip/bzip2 标准库就有；7z 需引入 `py7zr` 新依赖）、**通用 XML**（现在只有 EVTX XML）。
- 需先定定位：**Auditd / Sysmon-for-Linux**（中难度）与 P8 已记录的「优先服务 Windows/Sysmon 应急响应」冲突。
- 不建议：**EVTXtract**（从未分配空间/内存镜像里 carver 出 EVTX）——高难度且超出「分析一份日志」的定位。

**④ 规则量 50% —— 有条件**
- 补转换器 → 2272 条可到约 **2400 条**。
- 到 4515 条**必须引入第三方规则源**（Zircolite 的 4515 是多来源合并：hayabusa / mbabinski / mdecrevoisier / joesecurity + Sigma）。这是产品决策，不是技术问题：要过许可证核查（我们的门禁只允许 4 种许可证）、格式适配、逐条误报筛查。
- 后果：规则量、耗时、内存同步上升（实测 2198 条社区规则 +7.1s）。

**⑤ Sigma 规则支持 67% —— 不建议做**
- 缺的是 **Sigma correlation 规范**（`event_count` / `value_count` / `temporal` / `temporal_ordered`）。
- **实测收益为 0**：SigmaHQ 仓库 3152 个规则文件里**含 `correlation:` 块的 0 条**；Zircolite 自己的 4515 条里也是 **0 条**——它只是「支持这个格式」，并不随附关联规则。
- 我们已有等价能力：时间窗聚合（`aggregate` + `window_seconds`）+ 跨记录关联（`correlation.py`）。为对标而做，违反项目「不为了做而做」的纪律。

**⑥ 导出格式 38% —— 有条件，优先级最低**
- 缺 Splunk(CIM) / Elastic(ECS) / OpenSearch / Timesketch / SARIF 五套模板。
- 难度低（纯输出映射，不碰引擎），但**没有明确消费方**——如果用户只用本项目界面，这五套是「为对标而做」。
- 后果：维护面增加；格式若与目标平台版本不符会导入失败，而我们没有那些平台可实测。

**⑦ 分发部署 67% —— 不建议做**
- 缺独立二进制（Zircolite 有 Linux x64/ARM64、macOS arm64、Windows x64/ARM64 六个包）。
- **硬约束**：Windows 上无法交叉编译 Linux/macOS 包，且本项目**没有 CI** → 六个平台里只能出 Windows x64 一个，其余「打了也没验过」。
- 这与项目「不假装支持」的纪律直接冲突，除非先有 CI。

### 一句话结论

**7 个里有 3 个建议做**（字段处理、检测性能、日志格式解析的一半），**2 个有条件**（规则量、导出格式——都卡在需求/产品决策而非技术），**2 个不建议**（Sigma 关联规则零收益、独立二进制受限于无 CI）。

**性价比最高的第一步**：转换器加 `windash` + `base64offset` + `|re` 隐式字段名 + 中间通配转正则 —— 只动 `sigma_import.py` 一个文件，实测可解锁 **107 条规则**，规则量 2272 → 约 2379。
